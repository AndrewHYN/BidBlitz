# BidBlitz MVP Product Specification\n\n## 1. Product statement\n\nBidBlitz helps a seller turn an item into a competitive live sale as quickly as possible.\n\nCore promise:\n\n> List it. Start the blitz. Get your price.\n\n## 2. Primary users\n\n### Seller\n\nSomeone who wants to sell an item quickly and transparently.\n\n### Buyer\n\nSomeone who wants to discover good items and compete for them through live bidding.\n\n### Operator\n\nThe marketplace owner who needs to see activity, fees, disputes, abuse signals, and transaction health.\n\n## 3. Primary journey\n\n### Seller journey\n\n1. Sign up or sign in.\n2. Tap Sell.\n3. Add 1 to 8 photos.\n4. Enter title.\n5. Select category and condition.\n6. Enter starting bid.\n7. Enter minimum bid increment.\n8. Select auction duration.\n9. Add location.\n10. Preview.\n11. Start auction.\n12. Monitor bids.\n13. Auction ends.\n14. Winning buyer is recorded.\n15. Seller sees next-step instructions.\n\n### Buyer journey\n\n1. Open home.\n2. See Live Now and Ending Soon.\n3. Open an auction.\n4. See photos, title, current bid, next bid, time remaining, seller rating, condition, and location.\n5. Bid.\n6. Receive authoritative confirmation.\n7. If another bidder wins, show clear outbid feedback.\n8. If the buyer wins, show a success state and transaction next steps.\n\n## 4. Pages\n\n### Public\n\n- /\n- /browse\n- /auction/[id]\n- /category/[slug]\n- /search\n\n### Authenticated\n\n- /sell\n- /sell/preview\n- /dashboard\n- /dashboard/buying\n- /dashboard/selling\n- /dashboard/watchlist\n- /profile/[username]\n- /notifications\n\n### Operator\n\n- /admin\n- /admin/auctions\n- /admin/users\n- /admin/transactions\n\nKeep operator UI separate from customer UI.\n\n## 5. Home page hierarchy\n\nAbove the fold:\n- concise value proposition\n- primary Sell CTA\n- search\n- Live Now rail\n- Ending Soon rail\n\nSecondary:\n- Browse by category\n- recently listed\n- trust/reputation explanation\n- how BidBlitz works\n\nAvoid a cluttered portal homepage.\n\n## 6. Auction card\n\nEvery auction card should make these visible without opening the item:\n- image\n- title\n- current bid\n- number of bids\n- time remaining\n- location\n- condition\n- live/ending state\n\nThe card should have one obvious action: View Auction or Bid.\n\n## 7. Auction detail\n\nDesktop:\n- media gallery on left\n- sticky auction panel on right\n- current bid prominent\n- next valid bid explicit\n- large Bid button\n- countdown prominent\n- compact bid history\n\nMobile:\n- image first\n- title + current bid\n- countdown\n- sticky bottom bid action\n- details below\n- bid history below\n\nNever bury the bid action below long descriptions.\n\n## 8. Bidding rules\n\nA bid is valid only when:\n- auction is live\n- user is authenticated\n- user is not the seller\n- bid is at least current bid + minimum increment\n- bid is not after the server-authoritative end time\n\nUse a unique request/idempotency key for bid submissions.\n\nHandle simultaneous bids transactionally so there is one authoritative winner/order.\n\n## 9. Auction states\n\nUse explicit states:\n\nDRAFT\nSCHEDULED\nLIVE\nENDING\nENDED\nSOLD\nUNSOLD\nCANCELLED\n\nDo not infer state only from a countdown in the browser.\n\n## 10. Anti-sniping\n\nWhen a valid bid lands inside the configured closing window, extend the auction by a small server-controlled amount.\n\nMake the extension deterministic and tested.\n\n## 11. Realtime\n\nRealtime should update:\n- current bid\n- bid count\n- outbid status\n- auction state\n- time synchronization hints\n- winner state\n\nThe server/database remains authoritative.\n\nPrefer Supabase Realtime Broadcast for the scalable design. A simpler Postgres Changes implementation is acceptable for the MVP only when isolated behind a realtime adapter.\n\n## 12. Money\n\nNever use floating point.\n\nUse integer minor units plus currency.\n\nExample: amount_minor = 39900, currency = USD\n\nFees must be derived server-side and stored with the transaction record.\n\nMVP should support calculating the platform fee and recording transaction state without requiring the first release to become a full custody/escrow product.\n\nDesign a provider-agnostic payment interface so regulated payment providers can be added later.\n\n## 13. Trust\n\nMVP trust primitives:\n- email/account verification\n- seller profile\n- completed sales count\n- buyer completed purchases count\n- ratings/reviews after completed transaction\n- report auction\n- report user\n\nDo not expose private contact information unnecessarily.\n\n## 14. Search and discovery\n\nStart with:\n- category\n- price range\n- condition\n- location\n- ending soon\n- newest\n- most bids\n\nSearch should tolerate simple user wording.\n\nDo not build an expensive search stack during the 3-day MVP.\n\n## 15. Image handling\n\n- Accept common image formats.\n- Enforce size/type limits server-side.\n- Generate optimized image variants.\n- Use responsive image delivery.\n- Lazy-load non-critical images.\n- Do not block the first meaningful paint on below-the-fold images.\n- Preserve aspect ratio and avoid layout shifts.\n\n## 16. Notifications\n\nMVP notification events:\n- auction published\n- someone outbid you\n- auction ending soon\n- you won\n- your auction sold\n- auction ended without sale\n\nUse in-app notifications first.\n\n## 17. Monetization\n\nStart with:\n- configurable successful-sale platform fee\n- optional featured auction placement\n\nDo not hardcode commercial percentages throughout the UI.\n\nKeep fee policy configurable.\n\n## 18. Performance targets\n\n- fast first render\n- no layout shift on image loading\n- minimal JavaScript on public browsing pages\n- responsive interactions on mid-range mobile devices\n- graceful behavior on slow network\n- realtime updates without full-page refresh\n\n## 19. Accessibility\n\nKeyboard navigation\nVisible focus states\nSemantic controls\nAccessible labels\nSufficient contrast\nReduced-motion support\nError messages tied to fields\nNo color-only status indicators\n\n## 20. SEO\n\nPublic auction pages should have:\n- meaningful metadata\n- Open Graph image\n- canonical URL\n- useful title/description\n- indexable content where appropriate\n\n## 21. Analytics\n\nTrack product events such as:\n- auction_created\n- auction_published\n- auction_viewed\n- bid_started\n- bid_succeeded\n- auction_won\n- auction_sold\n- transaction_completed\n- seller_boost_purchased\n\nAvoid collecting unnecessary personal data.\n\n## 22. Testing\n\nCritical automated coverage:\n- seller cannot bid on own auction\n- invalid bid rejected\n- concurrent valid bids serialized safely\n- bid after closing rejected\n- anti-sniping extension works\n- auction closes once\n- winner is deterministic\n- fee is calculated correctly\n- RLS prevents unauthorized mutation\n- buyer/seller dashboards reflect state\n\nBrowser tests should cover the main journey on desktop and mobile.\n\nUse Playwright for end-to-end/browser verification and include a local web-server configuration. Visual/regression checks should cover the most important auction and sell flows.\n\n## 23. Definition of MVP ready\n\nA release is ready only when a real browser can complete:\n\nseller signs in -> creates auction -> publishes -> second user opens it -> second user bids -> first user receives realtime update -> another bid can supersede it -> auction closes -> winner is recorded -> seller sees sale -> fee is recorded.\n\nThen verify the same core experience on a mobile viewport.\n\n## 24. Explicitly out of scope for the first 3 days\n\n- native iOS/Android apps\n- complex shipping integrations\n- international tax engine\n- full escrow/custody\n- crypto wallet infrastructure\n- AI pricing\n- social feed\n- direct messaging\n- loyalty points\n- large ad system\n- multi-country compliance framework\n\nBuild the transaction loop first.\n
